# Requirements Document

## Introduction

This feature replaces the hardcoded gallery category system with a dynamic, Firestore-backed category management system. Admins will be able to create, edit, reorder, and delete gallery categories (tabs) from the admin panel without code changes. The public gallery page and admin gallery upload form will read categories from Firestore at runtime instead of from a static TypeScript file.

## Glossary

- **Category_Manager**: The admin interface for creating, editing, reordering, and deleting gallery categories.
- **Gallery_Category**: A Firestore document in the `gallery_categories` collection representing a single tab/filter on the gallery page.
- **Public_Gallery**: The public-facing gallery page at `/gallery` that displays images filtered by category tabs.
- **Admin_Gallery**: The admin gallery page at `/admin/gallery` used for uploading and managing gallery images.
- **System**: The Blooming Tastebuds Next.js application.
- **Admin**: A user with the `admin` role who has access to the admin panel.

## Requirements

### Requirement 1: Store Gallery Categories in Firestore

**User Story:** As an admin, I want gallery categories stored in Firestore, so that categories can be managed dynamically without code deployments.

#### Acceptance Criteria

1. THE System SHALL store each gallery category as a document in a `gallery_categories` Firestore collection with fields: `id`, `slug` (unique identifier string, lowercase alphanumeric and hyphens only, maximum 60 characters), `label` (display name, maximum 50 characters), `order` (non-negative integer for sort position), `isVisible` (boolean controlling public visibility), and `createdAt` (server timestamp).
2. WHEN a page or API route requires gallery categories, THE System SHALL read Gallery_Category documents from the `gallery_categories` collection ordered by the `order` field in ascending order.
3. THE System SHALL treat the `slug` field as the category value stored on gallery image documents in the `category` field.
4. IF the `gallery_categories` collection is empty or the Firestore read fails, THEN THE System SHALL fall back to displaying the two default categories (`cooking-classes` with label "Cooking Classes" and `personal-gallery` with label "Personal Gallery") in that order.

### Requirement 2: Admin Can Create Gallery Categories

**User Story:** As an admin, I want to create new gallery categories, so that I can add new photo groupings as the business grows.

#### Acceptance Criteria

1. WHEN an admin submits the create category form with a valid label, THE Category_Manager SHALL create a new Gallery_Category document in Firestore with a slug generated by trimming the label, converting it to lowercase, replacing spaces with hyphens, removing characters that are not alphanumeric or hyphens, and collapsing consecutive hyphens into one; with `isVisible` defaulting to `true`; and with `order` set to the highest existing `order` value plus 1, or 1 if no categories exist.
2. IF an admin submits a label that, after trimming leading and trailing whitespace, is empty or exceeds 50 characters, THEN THE Category_Manager SHALL display a validation error indicating the allowed length and prevent submission.
3. IF an admin submits a label that generates a slug already used by an existing Gallery_Category, THEN THE Category_Manager SHALL display a validation error indicating the category name is already taken and prevent submission.
4. IF the Firestore write fails when creating a Gallery_Category, THEN THE Category_Manager SHALL display an error message indicating the category was not created and preserve the admin's form input.

### Requirement 3: Admin Can Edit Gallery Categories

**User Story:** As an admin, I want to edit existing gallery categories, so that I can rename or hide categories as needed.

#### Acceptance Criteria

1. WHEN an admin updates the label of an existing Gallery_Category with a value that is non-empty and does not exceed 50 characters, THE Category_Manager SHALL update the `label` field in Firestore without changing the `slug` field.
2. WHEN an admin submits an edited label that is empty or exceeds 50 characters, THE Category_Manager SHALL display a validation error and prevent the update.
3. WHEN an admin toggles the visibility of a Gallery_Category, THE Category_Manager SHALL update the `isVisible` field in Firestore.
4. WHILE a Gallery_Category has `isVisible` set to `false`, THE Public_Gallery SHALL exclude that category from the tab navigation and filter options.
5. WHILE a Gallery_Category has `isVisible` set to `false`, THE Public_Gallery SHALL hide images assigned to that category from the category-filtered views but SHALL continue to display them under the "All Photos" tab.
6. IF the Firestore update fails when an admin edits a Gallery_Category, THEN THE Category_Manager SHALL display an error message indicating the update was not saved and SHALL preserve the admin's unsaved changes in the form.

### Requirement 4: Admin Can Reorder Gallery Categories

**User Story:** As an admin, I want to reorder gallery categories, so that I can control the tab display order on the public gallery.

#### Acceptance Criteria

1. WHEN an admin moves a category up or down in the list, THE Category_Manager SHALL update the `order` field of all affected Gallery_Category documents in a single batch write to reflect the new contiguous positions starting from 1.
2. IF an admin attempts to move the first category up or the last category down, THEN THE Category_Manager SHALL keep the list unchanged and not perform any write operation.
3. THE Public_Gallery SHALL display category tabs in ascending `order` field sequence.

### Requirement 5: Admin Can Delete Gallery Categories

**User Story:** As an admin, I want to delete gallery categories that are no longer needed, so that the category list stays clean and relevant.

#### Acceptance Criteria

1. WHEN an admin requests deletion of a Gallery_Category that has no images assigned to it, THE Category_Manager SHALL delete the Gallery_Category document from Firestore.
2. WHEN an admin requests deletion of a Gallery_Category that has images assigned to it, THE Category_Manager SHALL display a warning indicating the number of affected images and require explicit confirmation before proceeding.
3. WHEN an admin confirms deletion of a Gallery_Category that has images assigned, THE Category_Manager SHALL reassign all affected images to the Gallery_Category with the lowest `order` value among the remaining categories before deleting the Gallery_Category document.
4. IF an admin requests deletion of the last remaining Gallery_Category, THEN THE System SHALL reject the request and display an error message indicating that at least one category must exist.
5. WHEN a Gallery_Category is successfully deleted, THE Category_Manager SHALL recalculate and update the `order` fields of all remaining Gallery_Category documents to maintain a contiguous sequence starting from 1.

### Requirement 6: Public Gallery Reads Categories Dynamically

**User Story:** As a visitor, I want to see the current gallery categories as tabs, so that I can filter photos by the latest available groupings.

#### Acceptance Criteria

1. WHEN the Public_Gallery page loads, THE Public_Gallery SHALL fetch Gallery_Category documents where `isVisible` is `true` from Firestore, ordered by the `order` field ascending, and render them as filter tabs within 3 seconds.
2. THE Public_Gallery SHALL display an "All Photos" tab as the first tab before all dynamic category tabs, regardless of category configuration.
3. WHEN a visitor selects a category tab, THE Public_Gallery SHALL display only images whose `category` field matches the selected Gallery_Category slug, ordered by the image `order` field ascending.
4. WHEN a visitor selects the "All Photos" tab, THE Public_Gallery SHALL display all images that belong to any visible Gallery_Category, ordered by the image `order` field ascending.
5. IF no visible Gallery_Category documents exist in Firestore, THEN THE Public_Gallery SHALL display all images without category filter tabs.
6. IF the Firestore fetch for Gallery_Category documents fails, THEN THE Public_Gallery SHALL display all images without category filter tabs and show an error message indicating that categories could not be loaded.

### Requirement 7: Admin Gallery Upload Uses Dynamic Categories

**User Story:** As an admin, I want the image upload form to show current categories from Firestore, so that I can assign images to any dynamic category.

#### Acceptance Criteria

1. WHEN the Admin_Gallery upload or edit form opens, THE Admin_Gallery SHALL fetch all Gallery_Category documents from Firestore ordered by the `order` field ascending and display them as options in the category dropdown.
2. THE Admin_Gallery category dropdown SHALL include all categories regardless of their `isVisible` status, enabling admins to assign images to hidden categories.
3. WHEN an admin submits the image upload or edit form, THE Admin_Gallery SHALL require a category selection before allowing submission.
4. WHEN an admin selects a category for an image, THE Admin_Gallery SHALL store the category `slug` value in the image document's `category` field.
5. IF the Firestore fetch for Gallery_Category documents fails when opening the upload or edit form, THEN THE Admin_Gallery SHALL display an error message indicating categories could not be loaded and disable the form submission.

### Requirement 8: Backward Compatibility with Existing Data

**User Story:** As a system operator, I want existing gallery images to continue displaying correctly, so that the migration to dynamic categories does not break the current gallery.

#### Acceptance Criteria

1. WHEN the System encounters a gallery image with a `category` value of `cakes`, `cookies`, or `breads`, THE System SHALL map that value to the `personal-gallery` dynamic category slug.
2. WHEN the System encounters a gallery image with an empty, undefined, or unrecognized `category` value, THE System SHALL map that value to the `cooking-classes` dynamic category slug.
3. WHEN the System is deployed with this feature, THE System SHALL seed the `gallery_categories` collection with the two existing categories: `cooking-classes` (label: "Cooking Classes", order: 1) and `personal-gallery` (label: "Personal Gallery", order: 2) if the collection is empty.
4. THE System SHALL preserve the existing `normalizeCategory` function behavior for all legacy category values (`cakes`, `cookies`, `breads`, empty, undefined, and unrecognized strings) as long as gallery image documents with those raw values exist in the `gallery` collection.
